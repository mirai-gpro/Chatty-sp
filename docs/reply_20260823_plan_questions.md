## 3. 技術的な確認事項

### 確認事項1 — 案1-A の `crossOrigin` について

提案書 §2-1:
```javascript
l.rel = 'preload'; l.as = 'fetch'; l.href = ...; l.crossOrigin = 'anonymous';
```

**`as` の不一致は §2-1 で警告されているが、`crossOrigin` にも同じ問題がある。**

- `crossOrigin = 'anonymous'` は `credentials: 'omit'` 相当
- 同一オリジンで `fetch(url)` を素で呼ぶと `credentials: 'same-origin'`
- **この不一致でも preload は再利用されず、二重取得になる**

zip は同一オリジン（`/avatar/*.zip`）なので、**`crossOrigin` を付けない版も候補**と考える。

**質問**: §2-1 の確認方法（DevTools Network の `.zip` 行数）に、`crossOrigin` あり／なしの比較を追加する形でよいか。それとも先に `getInstance()` の内部（`fetch` か `XMLHttpRequest` か、credentials の指定）を確認すべきか。

※ これは Web プラットフォームの挙動であり、LAM/A2E・LiveAPI の知識ベース外領域ではない。ただし**実測での確認が必要**という認識。

### 確認事項2 — preload が効かなかった場合、アプリの待ち時間は変わらない

案1-A は「ブラウザが先に DL を始める」だけで、**`GaussianSplatRenderer.getInstance()` が呼ばれるタイミング自体は変わらない**（`linkLamAvatar()` のまま）。

- preload キャッシュにヒットすれば → `getInstance()` が即座に完了
- ヒットしなければ → **DL は2回走り、アプリの待ち時間は現状と同じかそれ以上**

**質問**: §2-4 の効果測定に「`[LAMAvatar] 3Dアバター初期化完了` までの時刻」が含まれているのは、この判定のためという理解でよいか。

### 確認事項3 — GAP ログ（§3-5）は正常起動でも出るか

**これが案1-A・案3-A の効果測定の可否を左右する。**

| 正常起動での挙動 | 帰結 |
|---|---|
| 小さい隙間が常時記録される | **常時データが取れる。再現待ち不要** |
| 不具合時しか出ない | **再現待ちになる** |

提案書はこの点に触れていない。

こちらの認識（**推定**）: `live-audio-manager.ts:218` の `Math.max(now + 0.005, this.nextPlayTime)` はマージンが 5ms しかなく、先読みもない。LiveAPI は音声をほぼリアルタイム速度で送るため、`nextPlayTime` が `now` を大きく上回る状況が構造的に作られていない。**したがって正常起動でも小さい隙間が記録される可能性がある。**

**ただし実測していない。** 1回デプロイして通常起動すれば分かる。

**質問**: この認識で合っているか。閾値 `gap > 0.01`（10ms）は妥当か、それとも最初は閾値なし（全件記録）にして分布を見るべきか。

### 確認事項4 — 案3-A は CLAUDE.md の「フォールバック禁止」に抵触しないか

提案書 §4-3 は `greeting_trigger` を **成功時・catch時・controller 不在時のすべて**から送る案。

**懸念**: 「アバターの初期化に失敗しても挨拶は進める」は、機能縮退での継続にあたる。CLAUDE.md 第4項「フォールバック禁止」に該当しないか。

**こちらの解釈**（確認したい）:
- 現状も 30 秒後には挨拶が始まる（`live_api_handler.py:759-764` はフェイルオープン）
- したがって案3-A は「30 秒待つ」を「即座」に変えるだけで、**新たなフォールバック経路の追加ではない**
- 該当しないと考えるが、判断を仰ぎたい
