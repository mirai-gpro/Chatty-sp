## 3. 実測で確定している事実

ユーザーが取得した5実行分のコンソールログ全文を解析した。

### 3-1. 不具合A — Gemini が音声パートなしでターンを返した

不具合A のログは全31行。`greeting_trigger送信` 以降は以下しかない。

```
[LessonController] greeting_trigger送信
256performance warning: READ-usage buffer ...
[LiveAPI] turn_complete          ← 届いている
[LiveAPI] greeting_done受信      ← 届いている
```

| 事実 | 根拠 |
|---|---|
| `live_audio` が0件 | `[Sync] StartTime reset to:` が0回 |
| `live_expression` も0件 | `[A2E Buffer]` が0回。**このログは `isTTSEnabled` ガードの影響を受けない**（`live_expression` ハンドラは `isLiveMode` のみ判定） |
| `turn_complete` / `greeting_done` は到着 | ログにあり |
| チャット欄にテキストは表示された | ユーザー報告 → `output_transcription` は届いていた |
| `isLiveMode = true` | `[LiveAPI] startLiveMode完了` |
| JS 例外なし | エラー行なし |

`live_expression` はサーバが A2E に PCM を送って初めて emit される。その PCM は
`live_audio` と**同じ行**（`live_api_handler.py:1044-1052`）から来る。

→ **`sc.model_turn.parts` に音声パートが1つも無かった。**

### 3-2. 不具合B — 再生側は正常。上流のチャンク途絶

正常起動（Step 2 後）の2ターン目で、同一機構の GAP 349ms を実測できた。

```
チャンク途絶       = 25.800 − 25.061 = 0.739 s
その時点の再生余裕 = 25.456 − 25.061 = 0.395 s
不足 + マージン    = 0.344 + 0.005   = 0.349 s   ← 実測 GAP と一致
```

`nextPlayTime` は `turn_complete` で更新されない（`onAiResponseEnded()` は触らない）ため、
**どのターンも余裕 5ms で始まる**（`live-audio-manager.ts:223`）。ジッタバッファは存在しない。

**そして途絶の最中に、別の Socket.IO イベントが届いている。**

```
[Socket] live_audio arrived bytes=5120          ← t≈25.061
[A2E] live_expression受信: chunk=0, frames=5    ← ★ 途絶の中
[A2E Buffer] chunk=0, +5frames, total=5         ← ★
[LAM ExprData] jawOpen=0.050, nonZero=10/52     ← ★ rAF 駆動
[Socket] live_audio arrived bytes=15360         ← t=25.800
```

時刻も確定する。直後の `[A2E Sync] offsetMs=381`（基準 25.800）＝実時刻 26.181 でカウンタ60到達。
カウンタはバッファが空でない間だけ増えるので起点は `[A2E Buffer] chunk=0` の行 → **25.181（途絶の120ms地点）**。
以降 `[A2E Sync]` は 381→1381→2381→3480→4480→5480→6480→7480 で **60 tick / 1000ms＝60.0fps 連続**。

→ **配送もメインスレッドも生きていた。`live_audio` が本当に届いていない。**

### 3-3. 不具合B 本体でもメインスレッドは正常

```
[A2E Sync] offsetMs=979,  frameIdx=29/61
           1979,  59/157      ← 間隔 1000ms
           2987,  89/157      ← 1008ms
           3984, 119/157      ← 997ms
           4981, 149/157      ← 997ms
           5979, 156/157      ← 998ms
```

**挨拶の全区間で 60fps。** さらに最初の行が `frameIdx=29/61` である＝バッファはフレーム0から
消費されていた＝カウンタは挨拶開始（≈2.46）から回っていた。**計測の死角は実質ゼロ。**

（そちらが `reply_20260823_phase1_answers.md` §2 で指摘した「計測の死角」は、
 構造的な指摘としては正しいが、**この実行には当てはまらなかった**。）

### 3-4. 旧フロー（2重リセット）の実際の動作

**当方は当初「旧フローでは挨拶がアバター初期化『前』に発火していた」と考えたが、実ログで否定された。**

## 4. コード上の差分 — 全数

`app_customer_support.py:942-946`（挨拶ガード）と `live_api_handler.py:757 / 773 / 816` の分岐により、
2回目の `live_start` は `session_count` が 2 になり**再接続ブランチ**に入る。

```python
# app_customer_support.py:942-946
if client_sid in greeted_client_sids:
    live_session.session_count = 1      # ← 2回目
else:
    greeted_client_sids.add(client_sid) # ← 1回目

# live_api_handler.py:757
self.session_count += 1                 # 2回目は 1 → 2

# live_api_handler.py:773 / 816
if self.session_count == 1:   → 初回ブランチ（30秒ゲート + send_client_content）
else:                         → 再接続ブランチ（send_realtime_input）
```

`resetAppContent()` は socket を張り替えない（`initSocket()` は `init()` で1回のみ、
`stopAllActivities()` に disconnect はない）ため `client_sid` は同一。

| # | 差分 | 2重リセット時代 | Step 2 後 | 当方の判定 |
|---|---|---|---|---|
| 1 | 発話するセッション | 2つ目（`session_count=2`） | 1つ目（`=1`） | #2 の前提 |
| **2** | **発話の指示方法** | **`send_realtime_input(text="続きをお願いします")`** | **`send_client_content(turns=dummy_text, turn_complete=True)`** | **唯一、音声生成に触れる** |
| 3 | 30秒ゲート | 通らない | 通る（`greeting_trigger` 待ち） | ゲート中は送受信データ無し |
| 4 | 発火時のアバター状態 | 初期化完了後（§3-4 で実証） | 初期化完了後 | **差分でない** |
| 5 | `_is_initial_greeting_phase` | False | True | Step 1 で A2E 経路は同一化済み |
| 6 | `clearPlaybackQueue()` | 挨拶直前に1回多い | なし | ターン冒頭は `nextPlayTime` が過去 → 効果ゼロ |
| 7 | `sleep(300)` + `/api/session/start` | 2回 | 1回 | チャンク到着に触れない |
| 8 | 旧セッションのスレッド | 30秒ゲートで残留（`stop()` は解除しない） | なし | 発話しない（`is_running=False`） |
| 9 | `_send_history_on_reconnect` | 呼ばれるが履歴が空で即 return（`:2140`） | 呼ばれない | 実質無操作 |

> **当方の解析では、本質的な差分は #2 の1つに絞られる。**
> **そして #2 は Gemini LiveAPI の仕様であり、当方の知識ベース外である。推論できない。**

### 案X — クライアントのみ、Cloud Run デプロイなし

## 9. 参考: 当方が別途特定した、本件とは独立の事項

**リップシンクのタイムライン基準が、ストリーミング経路（パス1）でずれている。**

仕様書 `docs/13` §2.2 / `docs/11` は「**条件1: `firstChunkStartTime` が音声再生開始時刻と一致**」と定める。
実装（`live-audio-manager.ts:307-312`）は `live_expression` chunk=0 到着時に基準を再設定するため、
**A2E の HTTP 往復時間の分だけ基準が後ろにずれる。**

実測（挨拶ターンのみ。2ターン目は途絶で汚染されるため除外）:

| 実行 | 初回アンカー | 再アンカー | ズレ | @30fps |
|---|---|---|---|---|
| 2重reset 実行1 | 1.571 | 1.880 | 309ms | **9.3フレーム** |
| 2重reset 実行2 | 1.821 | 2.120 | 299ms | **9.0フレーム** |
| 不具合B | 2.312 | 2.461 | 149ms | **4.5フレーム** |
| 正常D | 1.192 | 1.272 | 80ms | **2.4フレーム** |
| 正常E | 1.040 | 1.301 | 261ms | **7.8フレーム** |

導入経緯は `380ec7d`（03-30 02:07）のコミットメッセージにある。

> "...not from a stale timestamp set by **early/ghost audio packets**."

**その "ghost packet" の正体は、各ターン1件目の `bytes=4`**（base64 4文字 → PCM 2バイト → 1サンプル ≈ 0.04ms）。
これが基準を約 40ms 早く確定させる問題を解こうとして、**代わりに 2.4〜9.3 フレームの遅れを持ち込んでいる。**

**本件（不具合A・B）とは独立の事項として、別途扱う。**
ユーザーは「1〜2フレームは許容、3フレーム以上は違和感」と評価しており、改善を希望している。
