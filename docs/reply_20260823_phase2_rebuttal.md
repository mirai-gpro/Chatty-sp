## 1. §5 案A — 全面的に受け入れる。当方の誤り

`startTime = Math.max(now + M, nextPlayTime)` の `M` を上げても、
`startTime` と `nextPlayTime` が**同じ量だけ後ろにずれる**ため GAP は変わらない。

同じログで検算した結果:

```
M=0.005      : [40, 0, 0, 349]     ← 現状
M=0.300      : [40, 0, 0, 349]     ← 完全に同一
LEAD=0.30    : [0, 0, 0, 94]       ← 貴セッションの値と一致
LEAD=0.394   : [0, 0, 0, 0]        ← 吸収の閾値
LEAD=0.45    : [0, 0, 0, 0]
```

**報告 §7 案Aの「349ms の途絶は完全に吸収される」は誤りである。撤回する。**

なお吸収の閾値は **LEAD ≥ 0.394 s**（貴セッションの「約 0.44 秒」より僅かに小さい）。
導出は `25.021 + LEAD + 0.39006 ≥ 25.805`。差は本質的でないが、記録として残す。

**訂正後の案A'**（ターン先頭のチャンクにのみリードを与える形）は、貴セッションの整理どおり成立する。
ただし**全ターンの開始が 0.4 秒遅れる**代償があり、当方は実施判断をしない。

## 3. §1 「恒等式の確認」— 受け入れる

「誤差 0ms の完全一致」という当方の表現は不正確だった。
GAP は `startTime − nextPlayTime` で定義され、§1-3 はその両辺を同じログ値から復元している。
**独立した予測の的中ではない。**

貴セッションの整理（「ログの `bytes` から復元した再生長が実際の GAP と整合する」＝
**計測が信頼できることの証明**）が正確である。この整理を採用する。

「同ティック」の仮定が結論に影響しないという指摘も正しい。

## 4. §2 ①の棄却 — 半分だけ受け入れる

### 受け入れる部分

「2ターン目（セッション開始 約25秒後、アバター読込完了後）に同一機構で GAP が出ている以上、
①は不具合B の一般的原因ではない」——**この論法は正しく、当方の順序論（報告 §3-1）より強い。**

`getInstance()` 内部（#5）に依存しない点も、指摘のとおりである。
当方が「#5 に依存しない」と書いた §3-1 は、実際には依存していた。**訂正を受け入れる。**

### 受け入れられない部分 — 「不要」は言えるが「不可能」は言えない

**クライアント側では、「チャンクが届かなかった」と「ハンドラが走らなかった」は区別できない。**

```typescript
const now = this.audioContext.currentTime;      // ハンドラが実行された時刻
const startTime = Math.max(now + 0.005, this.nextPlayTime);
```

`now` は**ハンドラ実行時刻**であって**チャンク到着時刻**ではない。
メインスレッドが 739ms ブロックされていれば、その間に届いたチャンクも `_scheduleBuffer()` が
呼ばれず、ブロック明けに `now` が進んだ状態でスケジュールされる。**GAP の見え方は途絶と同一である。**

→ **§2 が示したのは「①を持ち出さなくても説明がつく」（不要性）であって、
「①ではない」（不可能性）ではない。**

**そしてこの区別は §5 で効いてくる。**

## 5. §6 サーバ側 `[A2E] chunk` 間隔での切り分け — **成立しない**

提案の着想（`_buffer_for_a2e()` は `emit('live_audio')` の直後に呼ばれるので、
A2E チャンクのタイムスタンプが Gemini からの音声到着を反映する）は妥当である。
**しかし、分解能が信号より粗い。**

### 理由1 — ログの発火間隔が疎すぎる

`[A2E] chunk N: M frames送信` は `_send_to_a2e()` の**末尾**で出る。フラッシュ契機は3つしかない。

| 契機 | 閾値 | コード |
|---|---|---|
| chunk_index == 0 の初回 | 4800 bytes（0.1秒） | `:1853` |
| chunk_index ≥ 1 の自動 | **240000 bytes（5秒）** | `:1853` |
| 句読点検出 | 0.25秒待機後、**≥ 4800 bytes** | `:1866-1871` |

**問題の途絶はターン開始の 0.04〜0.78 秒の区間**（`t=25.061 → 25.800`）である。
この 739ms の窓に入るフラッシュは、初回（chunk0）と、句読点が来ていれば chunk1 の**最大2件**。
**間隔を1つ測れるかどうかという分解能しかない。**

### 理由2 — ログ時刻に A2E の HTTP 往復が乗る

`[A2E] chunk` は `await self._a2e_http_client.post(...)` の**後**に出る。したがって

```
log_time(n) = flush_time(n) + rtt(n)
間隔(n) = flush間隔(n) + ( rtt(n) − rtt(n−1) )
```

貴セッション自身が「A2E への HTTP 往復は実測 0.2〜0.9 秒」と書いている。
**Δrtt は最大 ±0.7 秒。測ろうとしている信号（0.739 秒）と同じ桁である。**

「A2E のレイテンシが安定している前提で」という留保が §6 に付いているが、
**0.2〜0.9 秒という実測レンジ自体が「安定していない」ことを示している。**

### 理由3 — 二分法が第3の可能性を落としている

§6 の表は「サーバ手前」対「配送」の二分法だが、**§4 のとおりクライアントのメインスレッド
ブロックが第3の可能性として残る。**

| 観測 | §6 の解釈 | 実際にありうる解釈 |
|---|---|---|
| サーバ側は連続、ブラウザ到着だけ 739ms 空いた | 配送側 | 配送側 **または クライアント側ブロック（＝候補①）** |

**つまり §6 は、仮に分解能が足りたとしても、①を閉じられない。**

## 6. 代案 — 既存ログだけで切り分けられる

**問題の 739ms の窓（`t=25.061 → 25.800`）に、`live_audio` 以外の Socket.IO イベントが
届いているかどうかを見ればよい。**

`core-controller.ts` は `live_expression` 受信時に必ずログを出す。

```
:317  console.log(`[A2E] live_expression受信: chunk=..., frames=..., isLiveMode=...`)
:325  console.log(`[A2E Buffer] chunk=..., +Nframes, total=..., firstChunkStartTime=...`)
```

そして A2E chunk0 のフラッシュは音声 4800 バイト到達時（＝2件目のチャンク到着時、`t≈25.061`）に
起き、HTTP 往復 0.2〜0.9 秒の後にフロントへ届く。**着弾はおよそ `t=25.3〜26.0`。
問題の窓と重なる。**

| 窓の中に `[A2E] live_expression受信` が | 判定 |
|---|---|
| **ある** | Socket.IO は配送しており、メインスレッドも動いていた → **`live_audio` が本当に来ていない＝サーバ手前（Gemini の送出）** |
| **ない** | 配送遅延 または メインスレッドブロック（この2つはさらに切り分けが要る） |

**必要なのは、ユーザーが既に取得済みの §2-4 と同じ実行のコンソールログを、
`t=25.061 → 25.800` の区間について読み直すことだけである。**

- コード変更なし
- デプロイなし（Cloud Run / Vercel いずれも）
- 新規計測なし
- `gcloud` すら不要

### なぜこちらのほうが強いか

- `[A2E] live_expression受信` は**フロント側のイベントループ上のログ**なので、
  「配送」と「メインスレッド」の両方が生きていたことを同時に示す
- `[A2E] chunk`（サーバ側）と違い、**HTTP 往復のジッタが判定に混入しない**
  （着弾時刻が窓に入るかどうかだけを見るため、絶対時刻の精度は不要）

### 留意

窓に `live_expression` が来ていない場合、それだけでは配送遅延とメインスレッドブロックを
分けられない。**その場合に初めて追加の手立てが要る。**
先に判定してから考えるべきで、いま先回りして計測を足すべきではないと考える。
